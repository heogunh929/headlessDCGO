# 디지몬 AI 아레나 — 요구사항정의서 (draft)

- 작성일: 2026-07-03
- 상태: **draft / 초기 요구사항** — 아레나 개발은 한참 후속(RL 로드맵 M6). 확정 아님, 변경 가능.
- 관련: [rl_training_environment_design.md](rl_training_environment_design.md)(엔진/어댑터·seat 프로토콜), [rl_development_roadmap.md](rl_development_roadmap.md)(M5 리그·M6 아레나).
- 성격: **요구사항정의서**(무엇을 만족해야 하는가). 상세 설계(어떻게)는 개발 착수 시 별도 설계서로.

## 1. 개요 / 목적
여러 사람이 각자 만든 디지몬 카드게임 AI(봇)를 대전시켜 레이팅으로 겨루는 **소규모 취미 아레나**.
헤드리스 C# 엔진을 심판으로 삼아, 참가자 봇들이 원격 접속해 대전한다. "대단한 상용 서비스"가 아니라
**가볍게 굴러가는 커뮤니티 래더**를 지향한다(정교함보다 지속 가동·낮은 참여 장벽 우선).

## 2. 범위
### 2.1 범위 내 (초기)
- 참가자 등록·인증(키 발급), 봇 원격 접속 대전, 심판·안티치트, 시간 관리, 최소 매치메이킹,
  레이팅·시즌, 리플레이 로그 제공(HTML 열람), 데이터 보존/청소.
### 2.2 범위 외 (초기, 후속 후보)
- 실시간 관전(브로드캐스트), 봇 코드/웨이트 업로드+샌드박스 실행, 덱빌딩 메타(초기엔 덱 규정 단순),
  정교한 매치메이킹(참조풀·쿨다운 등), 공식 리플레이 뷰어의 고급 UI, 토너먼트/시즌 자동 스케줄러.

## 3. 액터
- **참가자**: 자기 머신에서 봇을 구동, 키로 접속해 대전하고 리플레이·전적을 조회.
- **봇**: 참가자의 프로그램. LLM·학습모델(SB3 등)·규칙기반·수동 등 종류 무관.
- **운영자(=개발자 본인)**: 서버 운영, 상주 봇 제공, 시즌/엔진 버전 관리.
- **서버**: .NET 엔진 심판 + 통신 + 기록. (봇 연산은 하지 않음.)

## 4. 확정 제약 (요구사항 수준의 결정 사항)
- **C-1 서버는 봇 연산을 하지 않는다.** 서버는 오직 엔진 심판·통신·기록만. 모든 신경망/추론 연산은
  참가자 부담(운영자가 전체 연산을 감당할 수 없음 = 하드 제약).
- **C-2 원격 에이전트(dial-out).** 봇은 참가자 머신에서 구동되어 서버로 접속. 서버는 제출 코드를 실행하지 않음.
- **C-3 봇↔서버 통신은 WebSocket + JSON.** 참가자에게 무거운 설치를 강요하지 않는다(언어 기본 기능으로 접속 가능).
- **C-4 서버가 게임의 유일 권위.** 게임 로직·상태·RNG는 전부 서버(엔진). 봇은 "정보집합 in → 액션 out" 엔드포인트.
- **C-5 봇 종류 무관.** 프로토콜은 봇 내부 구현(LLM/학습/규칙/수동)에 독립.
- **C-6 소규모 지향.** 레이팅 정밀도·매치메이킹 고도화보다 "판이 계속 돌아감"과 낮은 참여 장벽 우선.

## 5. 기능 요구사항 (FR)

### 5.1 참가 / 인증
- **FR-1.1** 사용자는 웹 화면에서 가입하고 **유니크 키**를 발급받는다.
- **FR-1.2** 봇은 그 키로 서버(매치 서비스)에 접속·인증한다. 키는 레이팅·전적 귀속의 신원이다.
- **FR-1.3** 참가자는 키로 본인의 전적·리플레이를 조회할 수 있다(타인 것은 불가).
- **FR-1.4** 시스템은 한 사람의 다중 계정 어뷰징(레이팅 펌핑)을 억제할 수단을 고려한다(초기 최소 수준).

### 5.2 봇 ↔ 서버 대전 통신
- **FR-2.1** 서버는 **행동할 좌석(mover)에게만** 그 좌석 시점의 관측과 합법행동 마스크를 전달한다.
- **FR-2.2** 봇은 합법행동 중 하나를 **액션 인덱스**로 응답한다.
- **FR-2.3** 관측은 봇 종류를 아우르도록 제공한다: **구조화 정보집합 JSON**(LLM·규칙기반 친화) +
  **고정 벡터 + factored 마스크**(학습모델 친화). 봇은 편한 형태를 소비한다.
- **FR-2.4** **합법행동이 1개뿐인 스텝은 봇에게 묻지 않고** 서버(어댑터)가 자동 진행한다. 그 결과는
  이후 관측(및 이벤트)으로 봇에 반영된다. (선택지 2개 이상 = "발동/안함" 포함 = 봇에게 질의.)
- **FR-2.5** 참가자에게 SDK 설치를 강제하지 않는다. **프로토콜 문서 + 복붙용 예제 클라이언트**를 제공한다.
- **FR-2.6** 프로토콜/관측/액션 스키마는 **버전을 명시**하고, 접속 핸드셰이크에서 버전을 교환한다(서드파티 계약).

### 5.3 심판 / 안티치트 (구조적)
- **FR-3.1** 서버는 각 좌석에 **정보집합만** 송신한다(상대 히든존·본인 시큐리티/덱은 룰상 모르는 정보로 제외).
- **FR-3.2** 봇의 액션은 합법 마스크로 검증한다. **불법 액션은 상태 변경 없이 거부**하며, 봇 버그로 간주해 몰수 처리한다(온보딩기 경고+기본행동 허용).
- **FR-3.3** 이벤트/자동 진행 결과를 봇에 전할 때도 **좌석별 시점 필터**를 적용한다(히든 정보 누출 금지).
- **FR-3.4** 대전 시드는 봇이 예측할 수 없어야 한다(셔플 예지 치팅 방지).

### 5.4 시간 관리
- **FR-4.1** 각 좌석은 **게임당 시간 뱅크(체스 시계식)**를 가진다(턴당 고정 아님).
- **FR-4.2** 단일 수에 **하드캡**을 둔다(무응답/무한루프 방어).
- **FR-4.3** 시간 설정(뱅크·증가분·하드캡)은 **핸드셰이크의 timeControl로 노출**하여 조정 가능해야 한다.
- **FR-4.4** 하드캡 초과 또는 뱅크 소진 시 **기본 합법행동으로 진행 후, 반복/소진 시 몰수**한다.
- **FR-4.5** 초기 시간값은 **가장 느린 봇(다단계 LLM)도 죽지 않을 만큼 관대하게** 시작하고, 로그를 보고 조정한다.
  (기준: "한 수 = API 1회" 봇이 다수파. 빠른 학습모델은 사실상 시간 무관.)

### 5.5 매치메이킹
- **FR-5.1** 접속 중인 봇들 중 대전 상대를 정해 매치를 시작한다(초기엔 단순 페어링으로 충분).
- **FR-5.2** **운영자 상주 봇(house bot)** 이 상시 접속하여, 참가 풀이 얇아도 최소한의 대전이 유지된다.
- **FR-5.3** 소규모 특성상 **중복 매칭·레이팅 출렁임을 허용**한다(정교화는 후속).

### 5.6 레이팅 / 시즌
- **FR-6.1** 매치 결과로 참가자 레이팅을 갱신한다(초기엔 단순 방식, 예: Elo 또는 승패 집계로 충분).
- **FR-6.2** 레이팅은 **시즌 단위로 운영**하며, 시즌 종료 시 **소프트 리셋**(평균 쪽으로 당김)한다.
- **FR-6.3** **시즌 경계 = 엔진 버전 경계.** 엔진의 큰 변경은 새 시즌으로 흡수한다(잦은 변경 대응).
- **FR-6.4** 시즌 최종 레이팅·순위는 영구 보존한다(명예의 전당).

### 5.7 리플레이 / 로그
- **FR-7.1** 실시간 관전은 제공하지 않는다.
- **FR-7.2** 참가자는 키로 **리플레이 로그(JSON)**를 조회·수신할 수 있다.
- **FR-7.3** 리플레이 JSON은 **자기완결적**이어야 한다 — 매 스텝의 게임판 상태(양쪽 존별 카드·메모리·시큐리티수·
  손패수·턴/페이즈·수행 액션·이벤트)를 담아, **엔진 없이도 재생 가능**하고 **엔진 변경에 영향받지 않는다.**
- **FR-7.4** HTML은 그 JSON을 파싱해 **박스 배치**로 게임판처럼 표시한다(이미지 불필요, 스텝 슬라이더 재생).
- **FR-7.5** 리플레이 JSON은 **공개·버전 명시 포맷**으로, 제3자가 자체 뷰어/분석기를 만들 수 있어야 한다.
- **FR-7.6** 리플레이가 만료(삭제)된 경우, 조회는 "만료됨"으로 우아하게 응답한다(전적 조회는 계속 가능).

### 5.8 데이터 저장 / 보존
- **FR-8.1** **레이팅·전적·매치메타**(누가/언제/결과)는 **DB에 영구**(시즌 스코프) 저장한다.
- **FR-8.2** **리플레이 원본**은 파일(HDD)에 저장하고, 요청 시 전송한다.
- **FR-8.3** 리플레이 원본은 **생성 약 1주 후 배치로 삭제**한다(경합 방지 위해 여유 TTL·날짜 폴더 분할 권장).
- **FR-8.4** 배치 삭제는 **리플레이 파일에만** 적용하고 DB(전적·레이팅)는 건드리지 않는다.
- **FR-8.5** DB 매치레코드와 리플레이 파일은 matchId로 연결한다.

## 6. 비기능 요구사항 (NFR)
- **NFR-1 참여 장벽 최소화**: 봇 작성자는 자기 언어 기본 기능(WebSocket+JSON)으로 접속 가능. 무거운 설치·SDK 불요.
- **NFR-2 서버 경량**: 서버 연산은 엔진 심판·통신·기록에 한정. 봇 연산 부하 0. 개인 PC/소규모 인프라로 운영 가능.
- **NFR-3 동시성**: 여러 매치를 병렬 호스팅하되, 한 매치는 턴제라 순차. 느린 봇이 다른 매치를 막지 않는다(비동기 I/O).
- **NFR-4 저장 경량성**: 무한 증가 데이터가 없어야 한다(리플레이=1주 TTL, 매치메타=시즌 스코프, 최종순위=극소 영구).
- **NFR-5 이식성/개방성**: 리플레이·프로토콜은 언어중립·버전명시 포맷으로 제3자 도구 제작이 가능해야 한다.
- **NFR-6 안티치트는 구조로**: 서버가 애초에 히든 정보를 안 보내고 불법을 거부 — 봇을 신뢰하지 않아도 안전.
- **NFR-7 개발 속도 수용**: 잦은 엔진 변경(현 개발 방식)을 시즌 경계·자기완결 리플레이로 흡수해 운영이 발목 잡히지 않는다.

## 7. 가정
- **A-1** 참가자는 자기 봇의 연산 자원(로컬 GPU/CPU 또는 외부 LLM API)을 스스로 부담한다.
- **A-2** 참가 규모는 소수(운영자 상주 봇 + 소수 참가자)에서 시작한다.
- **A-3** 봇의 다수는 "한 수 = 외부 LLM 1회 호출" 수준으로 구현된다(다단계 추론은 자기 시간 뱅크로 감당).
- **A-4** 엔진(룰·카드)은 개발 중이라 자주 변한다 — 시즌·버전 경계로 관리한다.
- **A-5** 재사용 자산: 엔진의 결정론·`LegalActionSetValidator`·정보집합 관측·seat 프로토콜(RL 설계 §5·§6)·
  `GameEvent`/셀프플레이 로그 포맷을 리플레이·심판에 재사용한다.

## 8. 향후 확장 (범위 외, 후속 검토)
- 봇 아티팩트 업로드+샌드박스 실행(서버가 연산 부담), 실시간 관전 브로드캐스트, 덱빌딩 규정·밸런스,
  정교한 매치메이킹(레이팅 근접·최근상대 쿨다운·참조풀), 공식 고급 리플레이 뷰어, 토너먼트/자동 시즌 스케줄러,
  레이팅 시스템 승급(Elo→Glicko-2/TrueSkill).
