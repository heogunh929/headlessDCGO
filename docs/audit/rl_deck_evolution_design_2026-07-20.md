# RL 학습환경 — 덱 관리 · 진화 트랙 아이디어 메모 (2026-07-20)

> **상태: 브레인스토밍 정리. 결정된 것 없음.** 사용자가 떠오르는 대로 이야기한 아이디어를 흩어지지 않게 모아두는 것이 목적이다. 아래 스키마/표/순서는 전부 "이런 형태면 되겠다"는 스케치일 뿐 확정안이 아니며, 실제 채택·형식·우선순위는 나중에 별도로 정한다.
>
> **다만 한 가지 전제만 깔려 있음(엔진 무접촉)**: 이 트랙 아이디어는 전부 엔진 진입점(매치 시작 시 양측 덱 카드-리스트 수신)의 **상류(上流) 소비자** 쪽 이야기다. 엔진 소스·관측/액션 공간·미러 로직은 건드리지 않는다는 것만 공통 바탕이고, 유일한 접점인 **진입 검증기**(밴리스트/제한/구성 규칙 — "엔진이 아니라 진입에서 막는다"의 그 레이어)도 엔진 밖에 산다.

---

## 0. 레이어 개관

```
[덱 소스층]  DeckProvider ─┐
                           ├─► 진입 검증기 ─► (concrete 덱 A, 덱 B) ─► [엔진: 매치 실행]
[진화 루프] Population ─────┘                                              │
     ▲                                                                     │
     └──────────────── 매치 결과(승/패·다이제스트) ◄─────────────────────┘
[로그층]  runs/<id>/*  ◄── 학습 루프 + 진화 루프가 append (읽기 전용 소비=대시보드)
```

- **DeckProvider**: "이번 판에 어떤 덱 쌍을 쓸지" 결정. 모드 = fixed / rotation / league / evolve.
- **진화 루프**: DeckProvider(evolve 모드)의 뒤를 받쳐, 세대 단위로 덱 **템플릿을 변이**시키는 바깥 루프. RL 학습 루프와 별개(판 중 덱 고정, 세대 단위로 덱 변화).
- **진입 검증기**: 엔진에 넘기기 직전 + 변이 후보 필터링에 **동일 코드 재사용**. 밴/제한/금지페어·구성 규칙(메인 50·디지타마 4·4장 제한)을 덱 전체 기준으로 계산.
- **로그층**: 학습·진화가 JSONL append만; 대시보드는 읽기 전용(추후 트랙).

## 1. 덱 정의 스키마 (아이디어 스케치)

두 층위를 구분한다.

- **Concrete 덱** — 해소된 `메인 50 + 디지타마` 카드 리스트. **엔진이 소비하는 것.**
- **덱 템플릿** — 그룹 + 제약. 진화/샘플링이 조작하는 것. 여러 concrete 덱으로 해소된다.

### 1.1 템플릿

```json
{
  "id": "exp-A",
  "format": "standard",                // 검증기가 적용할 밴리스트/규칙 세트 id
  "digitama": {
    "mode": "locked",
    "cards": ["ST1_01 x4"]
  },
  "main": {
    "size": 50,
    "groups": [
      { "id": "core",  "size": 20,       "mode": "locked",
        "cards": ["BT18_065 x4", "Vemmon x4", "..."] },
      { "id": "flex",  "size": 25,       "mode": "whitelist",
        "pool": { "color": ["Black"], "level": [3, 6] },
        "mutation_rate": 2 },            // 세대당 최대 교체 장수
      { "id": "wild",  "size": [3, 7],   "mode": "random",
        "pool": "all-ported",
        "mutation_rate": "full" }        // 매 세대 전량 재추첨
    ]
  }
}
```

### 1.2 그룹 모드

| mode | 변이 대상 | 후보 풀 |
|---|---|---|
| `locked` | 없음(불변) | — |
| `whitelist` | 그룹 슬롯만 | `pool` 필터(색/레벨/특징/명시 리스트) 내 |
| `random` | 그룹 슬롯만 | 지정 풀 전체(`all-ported` = 현재 포팅 카드풀) |

### 1.3 필드 규칙

- **`size`**: 정수 또는 `[min, max]`. 범위면 그 그룹 장수 자체가 탐색 대상(다른 그룹이 나머지를 채워 총합 = `main.size`).
- **`pool` 필터**: `color` / `level`(범위) / `trait` / `cards`(명시 화이트리스트)의 AND 조합. `"all-ported"`는 특수값.
- **`mutation_rate`**: 정수(세대당 최대 교체 장수) 또는 `"full"`(전량 재추첨). 그룹별 차등 = "안정 코어 + 탐색 외곽" 구조.
- **하한 고정 관용구**: locked 그룹 대신 whitelist + `cards`에 최소 매수를 두고 그 매수를 size로 잠그면 "Vemmon 최소 4장 유지, 나머지 자유"가 표현됨.

### 1.4 불변식 (검증기가 강제, 그룹을 가로질러 계산)

1. `Σ group.size` (해소값) `== main.size`, 디지타마 규칙 별도 충족.
2. 4장 제한·밴·금지페어는 **덱 전체** 기준. 예: locked에 BT18_065 4장 → wild 그룹은 5장째를 뽑을 수 없게 변이 후보에서 **자동 배제**.
3. 위반 후보는 생성 단계에서 제거(무효 concrete 덱이 엔진에 도달하지 않음).

> **구현 유의점(유일한 난점)**: 변이 연산자는 슬롯을 **그룹 안에서** 고르되, 후보 적법성은 **검증기를 재사용해 덱 전체로** 판정. 이 두 스코프 분리만 지키면 나머지는 순수 함수.

## 2. DeckProvider 계약

```
IDeckProvider:
    NextMatchup(runState) -> (DeckSpecA, DeckSpecB)     // 판 시작마다 호출
    ReportResult(matchup, result)                        // 승/패·다이제스트 피드백
```

| provider | 동작 | 용도 |
|---|---|---|
| `fixed` | 지정 덱 쌍 고정 | 재현 실험·**평가 기준선** |
| `rotation` | 덱 풀에서 판마다 추첨(균등/가중) | 매치업 일반화 |
| `league` | 승률 통계 기반 어려운 매치업 우선 추첨 | 커리큘럼 학습 |
| `evolve` | population에서 추출(§3) | 덱 구축 탐색 |

스키마: 런 설정에 `provider: { mode: fixed|rotation|league|evolve, ... }` 한 필드.

## 3. 진화 루프 (evolve 모드 뒷단)

바깥 루프 = 세대. 각 세대 = 다수 매치(내부에서 RL 정책 구동). 매치 결과 → 적합도 → 선택/변이 → 다음 세대.

### 3.1 연산자

- **변이**: §1 그룹 규칙대로 그룹 내 교체. 검증기 통과분만 채택.
- **교차(선택)**: 두 덱 간 **그룹 단위** 교환(같은 그룹 id끼리).
- **선택**: 토너먼트 또는 절단(truncation).

### 3.2 다양성 처방 (수렴/순환 방지 — 목적별 선택)

`diversity: none | hall-of-fame | niching | nash`

| 옵션 | 효과 | 언제 |
|---|---|---|
| `none` | 순수 승률 최대화 → 지배 덱 있으면 붕괴, 없으면 순환 | 최강 에이전트만 목표 |
| `hall-of-fame` | 역대 챔피언을 상대 풀에 영구 보존 → 순환 퇴행 방지 | 강건성 |
| `niching` | "남이 못 잡는 덱을 잡는" 덱에 가산 → 아키타입 분화 | 다양성 보존 |
| `nash` | 챔피언 1개가 아닌 **인구 분포** 상대 승률로 적합도 → 수렴점=덱 혼합 균형(메타 점유율) | 밸런스/메타 실험 |

### 3.3 승격 파이프라인 (탐색→고착)

`wild`(전체풀 랜덤) 그룹 = **돌연변이 주입구**. 화이트리스트 밖 카드가 성적을 내면 다음 세대에 그 카드를 `flex`(whitelist)로 **승격**시키는 규칙(성적 기반) → 탐색과 고착이 이어짐. (옵션 플래그로 on/off.)

### 3.4 단일 수렴 논점 (기록)

- 카드풀에 **지배 덱**이 있으면 소박한 진화는 시작점 무관하게 거기로 붕괴 — 이는 실패가 아니라 **카드풀 진단**(밴/제한이 필요하다는 신호).
- 메타가 **비전이적**(가위바위보)이면 단일 수렴점 없이 **순환** → HoF/niching/nash로 관리.
- **서로 다른 코어를 고정한 인구를 병렬 실행**하면 아키타입별 최적화가 병렬로 되며 단일 수렴이 자연 완화.

## 4. 로그·런 스키마 (아이디어 — 대시보드 소급 표시를 염두에)

```
runs/<run-id>/
  config.json          # 하이퍼파라미터 + provider/진화 설정 + engine_commit(환경 버전)
  generations.jsonl    # 세대별: 적합도 분포·챔피언 덱·다양성 지표
  matches.jsonl        # 판별: 덱 쌍·승자·스텝수·trajectory 다이제스트 참조
  eval.jsonl           # 고정-덱 평가 결과(학습과 분리 표기)
  checkpoints/         # 정책 스냅숏
```

- **`engine_commit` 필수**: 어느 엔진으로 배운 정책인지 추적(B군 flip에 의한 액션/관측 공간 churn 관리 지점).
- **평가 분리 원칙**: 학습은 sampling/evolve, **평가는 고정 덱 세트**로 — 덱과 정책이 동시에 변하면 승률 원인이 섞이므로 `eval.jsonl` 별도 표기.

## 5. 대시보드 (추후 트랙 — 스키마만 예약)

3+1 모듈. 지금은 만들지 않음; §4 로그 형식이 계약.

1. **런 트래커**: 런 목록·winrate/eval/스텝속도 곡선·하이퍼파라미터·`engine_commit`.
2. **덱 매니저**: 템플릿 CRUD·그룹(locked/whitelist/random) 편집 UI·포팅 카드풀 브라우저(포팅분만 필터)·매치업 매트릭스.
3. **에피소드 인스펙터**: 기존 trajectory 다이제스트/이벤트 로그 재사용해 판을 스텝 재생(legal-set·선택 액션·보상) — 학습 디버깅 + 엔진 QA(이상 행동=갭 신호) 겸용.
4. (선택) **워커 상태**: 코어별/원격 처리량·생존.

스택 권고: 로컬 웹(FastAPI + 정적 프론트) — 엔진 PC/모델 PC 분리 구상과 호환. 급하면 곡선은 TensorBoard로 대체, 2·3만 커스텀.

## 6. 만든다면 이런 순서 (스케치 — 전부 엔진 독립이라 틈새/병행 가능)

| 배치 | 내용 | 규모 | 선행 |
|---|---|---|---|
| E1 | **스키마 고정**: 덱 템플릿·provider·런 로그 JSON 계약 확정 + 검증기 규칙 세트(format) | S | — |
| E2 | DeckProvider 4모드 + 진입 검증기 재사용 배선 | S~M | E1 |
| E3 | 그룹-제약 변이 연산자(locked/whitelist/random·size 범위·검증기 필터) + 단위 테스트 | M | E1 |
| E4 | 진화 루프(population·적합도·선택) + diversity 옵션(none/HoF/niching/nash) | M | E3 |
| E5 | 승격 파이프라인 + 병렬 인구 실행 | S | E4 |
| E6~ | 대시보드 3모듈 | M | §4 로그(E1) |

- **정답 없는 자유 설계**라 AS-IS 대조·적대 리뷰 부담 없음; 검증은 "변이 결과가 제약을 지키는가"의 순수-함수 단위 테스트.
- **진짜 난점은 코드가 아니라 실험 설계**(diversity 튜닝·세대 크기·변이율·평가 판수) — 본학습에서 반복 조정하는 영역이라 사전 확정 불가, 인프라 유연성으로 흡수.

## 7. 실험-설계 미결(본학습 시 결정 — 인프라는 미리 유연화)

- 정책 vs 덱 **공진화 케이던스**(정책 고정한 채 덱만 진화 세대 N vs 동시 공적응).
- 적합도 = 단순 승률 vs Nash 분포.
- 세대 크기·인구 크기·변이율·매치업당 판수.
- `diversity` 기본값(목표가 최강 에이전트면 none 허용, 메타/밸런스면 nash/niching).
