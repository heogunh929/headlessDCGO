## 1. 배경과 목적

- **[확정 — 프로젝트 목표 (2026-07-30 사용자 명시)]**
  - **1차 목표**: RL 학습환경을 만든다 (= 현행 로드맵의 목표).
  - **2차 목표**: **불특정 다수의 LLM이 서버에 붙어 대전하는 AI 아레나 개최**까지.
  - 이 툴의 요구사항은 1차 목표(본학습)를 직접 받치되, 2차 목표(아레나)로 가는 길을
    막는 결정을 해서는 안 된다 — 특히 서버·대전 서빙·관전(판 뷰어)·순위(이력) 표면은
    아레나의 전신이 될 수 있다.
- **[확정]** 본학습(L0 규모) 착수 전에 관리 툴이 있어야 한다.
- **[확정]** 기존 `rl/dashboard`는 "원하는 것이 거의 들어있지 않다" — 참고는 하되 그것의 확장이 목적이 아니다.
- 배경 사실: 2026-07-30 결함 사슬 6건 수리 과정에서 런 유실(timeout으로 정책 소실),
  결함 로그 증발(stderr 미수집), 런 간 비교 수작업, 판 내부 관찰 불가 등이 실제로 발생했다.

## 2. 핵심 능력 4가지 [확정 — 2026-07-30 선택]

| # | 능력 | 한 줄 정의 |
|---|---|---|
| ① | 판 들여다보기 | 끝난 판을 사람이 열어 상태 전개를 본다 |
| ② | 학습 운영 | 학습을 걸고·멈추고·지켜본다 |
| ③ | 런 이력·비교 | 지난 런들을 등재하고 견준다 |
| ④ | 결함 감시 | 엔진 결함 신호를 수집·열람한다 |

- **[확정]** 형태는 **웹 기반 서버**이고, **서버가 명령을 실행할 수 있어야** 한다
  ("명령 실행이 안 되면 가능한 것에 제약이 많다").

## 3. ① 판 들여다보기 — 상세 요구

- **[확정]** 매 판 종료 시 **그 판의 내용을 담은 로그 파일**을 만든다.
- **[확정]** 뷰어는 **로그 파일을 읽어** 상태 스냅샷을 보여준다 (엔진 재실행 방식이 아님).
- **[확정]** 화면 디자인은 첨부 와이어프레임(`dcgo_replay_wireframe_responsive_fixed.html`) 느낌:
  - 양측 플레이 시트(상대 180° 회전): 시큐리티(장수+목록) · 배틀에어리어(카드 슬롯 그리드) ·
    육성(디지타마/육성 슬롯) · 덱 / 트래시 / 게임 정보
  - 중앙 메모리 게이지(±10, 현재 위치 표시)
  - 우측: 이벤트 로그(시각·유형·설명, 검색, 유형 필터 칩, 클릭 시 해당 시점 이동)
  - 우측 하단: 상태 스냅샷 패널 — **요약 / Diff / JSON** 탭
  - 하단: 재생 컨트롤(처음/이전/재생/다음/끝, 배속 0.5~4x) · 타임라인(턴 마커) ·
    옵션 토글(숨김 정보 보기 · 효과 대상 강조 · 디버그 표시)
- **[확정]** 기록 범위(어떤 판을 기록할지)는 **툴에서 설정 가능**해야 한다.
- **[승인]** 스냅샷 앵커는 **결정(스텝) 시점** — 그 사이 이벤트는 텍스트로 싣고,
  Diff는 스텝 간 비교로 구현. ("일단 그대로 가고" — 잠정 승인, 재론 가능)
- **[승인*]** 로그 파일에 시드·액션열 병기 — 추후 "이 시점부터 이어돌리기" 디버깅 여지.
- **[승인*]** 로그엔 항상 전정보(양측 손패·시큐리티 내용·덱 순서) 기록, 가리기는 뷰어 토글.
- **[승인*]** 카드 표시는 1차 텍스트(카드명·ID·레벨·DP·서스펜드·진화원 스택), 이미지 2차.
- **[승인*]** "효과 대상 강조" 토글은 2차(이벤트에 구조화된 대상 정보 필요 — 1차는 텍스트 서사).
- **[승인 2026-07-30]** 이벤트 칩 = 전체/페이즈/효과/배틀 + **선택** 추가.
- **[승인 2026-07-30]** "게임 정보/선택 이벤트" 박스 = 그 시점의 결정(좌석·선택 내용)과 합법 행동 수.
- **[승인 2026-07-30]** 디버그 토글 = 스텝 인덱스·액션 마스크·tick 번호 표시.

## 4. ② 학습 운영 — 상세 요구

- **[확정]** 서버에서 학습을 기동·정지할 수 있어야 한다.
- **[승인 2026-07-30]** 런처 조정 항목 = 스텝 수 / 시드 / 덱·레시피 / 워커 수 / 기록 모드 /
  체크포인트 주기·보존 수 / eval 판수.
- **[승인 2026-07-30]** 모니터링 = 진행률 / 승률 추이 / RSS(엔진 PC·학습기 각각) / 처리량 /
  결함 카운터 실시간.
- **[승인*]** 정지 = 체크포인트 저장 후 종료(graceful), 강제 종료는 별도.
- **[승인*]** 체크포인트 주기·보존 개수는 기동 설정에 포함(기본 2,000스텝/최근 5개).
- **[승인*]** 학습 잡은 동시 1개 강제(현 훈련 PC 13GB RAM·워커 6 현실).

## 5. ③ 런 이력·비교 — 상세 요구

- **[승인 2026-07-30]** 비교 지표 = eval 승률·CI / 판 사유 분포 / 처리량 / 스텝 수 /
  엔진 git sha / 시드 / 덱 구성 / 학습 곡선(승률·보상 추이).
- **[승인*]** 런 메타 2단계 기록: 시작 시 config·엔진 git sha·시드·시작시각, 종료 시 지표·census 병합
  — "이 정책이 어떤 엔진에서 나왔나"를 기계 판정 가능하게.
- **[승인*]** 과거 런(l0-main-1~4)은 소급 등재하지 않음(결함 엔진산, 폐기 대상).

## 6.5 ⑤ 아레나 골격 (2차 목표의 1차 편입분) [확정 — 2026-07-30]

- **[확정]** 1차 범위에 아레나 **골격을 일부 포함**한다 (전체 아레나가 아니라 기반).
- **[확정]** 대전 API는 **웹소켓(WebSocket)** 으로 한다.
- **[확정]** **실시간 관전은 불필요** — **종료 후 관전**(= ① 판 뷰어)으로 충분하다.
- **[확정]** **순위 열람은 필요**하다.
- **[확정]** API를 외부에 뚫어야 하므로 **관련 관리 페이지와 가입 페이지가 따로** 있어야 한다.
- **[승인 2026-07-30]** 골격 경계 = **한 판 완주 수준 실동**: 웹소켓으로 테스트 클라이언트가
  붙어 실제 한 판을 둘 수 있어야 한다(프로토콜 실전 검증).
- **[승인 2026-07-30]** 가입 = **관리자 승인제 + 자동 승인 기능**(관리 페이지에서 자동/수동 전환).
- **[승인 2026-07-30]** 순위 = **시즌/리그 구분** 있는 순위 체계.
- **[승인 2026-07-30]** 대전 성립 = **열린 래더 + 상대 지정 도전 병행**.
- **[승인 2026-07-30]** 1차 골격 = 스키마에 시즌 필드만 갖고 단일 시즌 운영.
  시즌 운영 규칙(기간·리셋·승강)은 아레나 본격화 때 확정.
- **[주의 — 제안 영향]** 웹소켓 + 가입/세션 관리가 들어오면 §8의 "stdlib 전용" 제안은
  유지가 어려움(http.server는 웹소켓 미지원). 최소 의존 추가(예: websockets/aiohttp 계열)로
  제안을 수정해야 할 것 — 확정은 설계 단계에서.

## 6.5.5 아레나 접속 방식 (2026-07-30 5차 문답 확정)

- **[확정]** 접속 = **A. 에이전트 상주 접속형**: 참가자의 에이전트가 API 키로 웹소켓 접속 →
  래더 큐/지정 도전 → 서버가 상태+합법 행동 push → 에이전트 착수 응답. 접속 끊김은
  유예 N초 내 재접속 허용, 초과 시 타임아웃 패와 동일 처리.
- **[확정]** 참가 채널 2종 (공통 기반 = 파이썬 SDK/프로토콜):
  ① **완성 러너**(CLI) — 설정(키·모델·프롬프트)만으로 래더 참가. 1차 "한 판 완주" 검증도 이것으로.
  ② **에이전트 플랫폼 스킬** — OpenClaw·Hermes Agent(Nous Research, OpenClaw 스킬 호환 확인
  2026-07-30 검색) — OpenClaw 규격 한 벌로 두 채널 커버. 프로토콜 안정화 후 포장.
- **[승인]** 서버 스택 = HTTP+웹소켓 통합(aiohttp 계열) — 상주 소켓 다수+페이지 동시 서빙.

## 6.6 아레나 상세 (2026-07-30 2차 문답 확정)

- **[승인]** 웹 서버(관리툴+아레나)는 **머신 무의존적으로** 만들고 배치는 나중에 결정.
- **[확정]** 우리 RL 정책은 **2차 구축 후 아레나 참가자로 들어간다** (1차 골격은 여지만).
- **[승인]** 착수 시간 = **착수당 제한(설정 가능) + 초과 시 타임아웃 패**.
- **[확정]** 덱 = **참가자가 자기 덱을 등록**한다.
  - 파생 요구: **덱 적법성 검증기** 필요 — 카드 실존·매수 제한 등 덱 구성 규칙 검증.
    검증 기준은 AS-IS의 덱 규칙이 정본(두 번째 오라클 금지 원칙 준수).
  - **[확정 2026-07-30 — 덱 관리 규칙]** 덱의 **정본은 서버**:
    ① 키당 복수 등록(이름 부여, 상한은 관리자 설정) + **활성 덱** 지정(래더는 활성 덱,
    지정 도전은 도전 시 선택). ② 참가자 페이지에 덱 관리 UI(허용 풀 브라우징 빌더,
    검증 실패 사유 즉시 표시) + 키 인증 덱 조회·등록 API. ③ 이력 메타·판 로그엔
    **판 시점 덱 스냅샷** 고정(사후 수정·삭제 무영향). ④ 카드 풀 축소 시 해당 덱은
    삭제 아닌 **비활성 표시**(풀 복귀 시 자동 복원). ⑤ 덱리스트 열람 = 본인+관리자만.
    ⑥ 에이전트 프로토콜은 덱 ID만 참조하되, **판 시작 메시지에 자기 덱 구성 전문을 동봉**
    (LLM이 자기 덱을 알아야 함 — 사용자 지적 2026-07-30). 판 중 스냅샷은 남은 장수만
    (덱 잔여 순서·내용은 실게임에서도 비공개 정보), 상대 덱리스트는 미제공.

## 6.6.5 RL 참가자·덱 관리 구분 (2026-07-30 문답 확정)

- **[확정]** RL 정책도 아레나에서는 **API 키를 발급받는 참가자** — 참가자 레코드에
  종류 표시(`kind: llm | policy(house)`, 순위표에 하우스 봇 투명 표기), 스냅샷별
  별도 참가자 등록 가능(버전별 레이팅 분리, L1 스냅샷 Elo와 접속).
- **[확정]** 혼성 매치 성립: RL(숫자 관측)·LLM(텍스트 ws)·랜덤 어느 조합이든 같은 판 —
  매치 브로커가 좌석 단위로 소비자를 라우팅.
- **[확정]** **덱 관리 이원화**: LLM(외부) 덱 = 서버 정본·참가자 등록·풀 검증 /
  RL 덱 = 학습 파이프라인 소유(레시피·잡 산출물, 풀 제약 없음).
  단 **덱 포맷(JSON)과 적법성 검증기는 공용**(아레나만 풀 필터 추가),
  두 세계의 연결은 **스냅샷 참가자 등록 게이트 하나**(그 시점에 검증+풀 통과 → 아레나 덱 등록).

## 7. 배치·환경 요구

- **[확정 2026-07-30]** **현재 PC = 엔진 전용** (RlBridgeHost 매치 시뮬레이션).
  **모델 학습은 1차적으로 DGX Spark에서** 돌릴 예정.
- **파생 요구 (확정의 귀결)**: 학습기(파이썬/DGX)와 엔진 호스트(닷넷/현 PC)가 **다른 머신**이므로,
  현행 stdio 서브프로세스 브리지를 **네트워크 브리지**로 확장해야 한다. 관측·행동·결과가
  LAN을 건너며, 워커 수 규약(엔진 PC 6워커)·RSS 상한은 엔진 PC 쪽 러너가 관리한다.
- 참고 사실: DGX Spark는 ARM64 + NVIDIA GPU — 학습 스택(torch/sb3)은 CUDA-ARM 빌드 필요,
  현행 CPU 고정(`device="cpu"`) 해제 대상. 엔진(.NET)은 현 PC에 남으므로 이식 불요.
- **[확정 2026-07-30 — 보안 표면 3분류]**
  1. **운영자 표면**(관리툴 UI·러너 명령 API·아레나 관리 페이지): 공유 토큰 1개, LAN 밖 비노출.
     아레나 본격 공개 시 관리자 계정제 승격 검토.
  2. **아레나 표면**(인증 참가자): API 키가 신원이자 권한 전부 — 대전 접속·본인 이력·덱 등록.
     키별 rate limit.
  3. **계정 발급 전 공유 표면**(비인증 공개): 가입 신청 페이지 + 공개 순위표만. 읽기 전용 원칙
     (쓰기는 가입 신청 하나, 승인제가 완충) + 신청 rate limit.
- **[확정 2026-07-30]** **공개 순위표는 로그 비공개** — 판 열람은 참가자 본인 판 + 관리자만.

## 7.5 확정된 운영 정책 (2026-07-30 문답)

- **[승인]** 아레나 신원 = **API 키 발급만** (핸들+키). 추후 확장 가능성만 열어 둠
  (스키마에 여지, 1차 구현은 최소).
- **[승인]** 결함 감시 알림 = **임계 알림까지** — 규칙(예: abort율 N% 초과 시 알림/중단)을
  설정할 수 있는 UI 포함.
- **[승인]** 판 로그 보존 = **용량 상한 로테이션** — 상한 초과 시 오래된 비사고판부터 삭제,
  사고판은 로테이션에서 제외(결함 census의 증거).

## 8. 비기능 요구

- **[임의 — §6.5 웹소켓과의 모순 해소]** 의존 최소 원칙은 유지하되, **웹소켓 서버 라이브러리
  1개만 예외 허용**(stdlib http.server는 웹소켓 미지원). 메일은 stdlib smtplib. UI는 바닐라 JS.
- **[승인*]** 명령 실행은 화이트리스트(학습·평가·리플레이)로 한정 — 임의 셸 불가.

## 8.5 임의 확정 (2026-07-30 위임분 — 이의 시 재론)

- **[확정 2026-07-30] 워커 수**: 런처에서 런별 조정, **상한 자체도 관리자 대시보드에서
  러너별로 설정**(기본 6 — rl-workers-six 규약 + OOM 이력 기준값). 상한 초과 기동은 러너가 거부.
- **[확정 2026-07-30] 임계 규칙의 액션**: 규칙별로 "알림만 / 알림+자동 중단" 선택,
  **기본값은 알림만**. 규칙·임계값·액션 전부 대시보드에서 관리.
- **[확정 2026-07-30] 판 로그 보존 기준은 관리자 대시보드에서 설정** — 용량 상한·보존 기간·
  시즌 단위 보존 등 규칙을 관리 UI에서 조정. 불변 원칙만 고정: 이력 메타(결과·상대·시즌·
  타임스탬프)는 영구 보존, 사고판은 삭제 제외.
- **[확정 2026-07-30] 판 로그 파일 규격**: 판당 1파일 `<매치ID>.jsonl.gz`
  (헤더 1줄: 시드·덱·엔진 git sha·참가자 + 스텝/이벤트 스트림). 판 진행 중 메모리 버퍼 →
  종료 시 일괄 압축 기록(스텝 핫패스에 압축 비용 0, 판당 ~0.1초 버스트 — 실측 기록량
  초당 1~2MB vs gzip 처리량 50MB/s+로 여유). 압축 레벨은 빠른 쪽 기본. 병목 실측 시
  "원본 기록 후 백그라운드 압축(성공 확인 후 원본 삭제)"로 전환.
  **뷰어는 `.jsonl.gz`만 읽는다** — 파일이 아직 없거나 준비 안 됐으면 "준비 중/없음" 안내만
  (실시간 관전 없음이 전제라 원본 직독 불필요 — 사용자 확정 2026-07-30).
  원본은 어느 경로에서도 최종적으로 남지 않는다.
- **[확정 2026-07-30] 시간 표기**: 모든 기록은 KST ISO8601.

## 9. 의도적 이연 (아레나 본격화 시점에 확정)

1. 아레나 API 외부 공개 방식(포트포워딩/터널/호스팅)과 보안 수위 (§7).
2. 시즌 운영 규칙 — 기간·리셋·리그 승강 (§6.5).
3. 신원 확장(이메일 등) — 1차는 핸들+API 키, 스키마 여지만 (§7.5).
4. 카드 이미지 표시·효과 대상 강조 — 2차 (§3).
5. **덱 진화 트랙** — 내 덱을 변이(몇 장 교체)→승률 평가→선택으로 강화하는 탐색 루프.
   1차 범위 밖, 별도 트랙. 토대(덱 검증기·판 로그·runner 잡 체계·시드-결정 프로바이더)는
   1차 설계가 이미 제공 — "새 잡 종류 하나"로 얹는 형태. 평가 비용(변이당 수십~수백 판)과
   정책-덱 공진화(상위 후보만 재학습 검증) 유의.
